## 1. 要解决的问题和当前真实基线

用户需要回答六个具体问题：①项目中哪些资产确实属于集团？②属于集团哪家省/市公司或专业子公司？③每个单位有哪些未完成的排查方向？④哪些信息是正常公开，哪些是疑似或已核实泄漏？⑤泄漏发生在自有系统、外部代码/文档平台还是被盗数据渠道？⑥谁负责整改，原泄漏与复测证据是什么？

## 2. 总体组织方式：先集团总账，省市划分并行开始

不要先逐省独立搜索再拼总量，也不要等全国全部整理完才开始逐省工作。第一轮把现有项目映射为一个集团总账，立即分出可解释的候选单位。可确认部分进入省/市工作台，模糊部分继续在待归属队列补证。

建议展示树：

```
集团总账（绑定现有 project，不移动资产）
├─ 集团总部 / 集团共享系统
├─ 省级经营单位
│  ├─ 浙江省公司
│  │  ├─ 省公司本部
│  │  ├─ 杭州市级单位 → 区县/分公司（有可靠目录才展开）
│  │  └─ 省内尚未细分资产
│  ├─ 江苏省公司
│  └─ 其他已导入省级公司
├─ 专业子公司
│  ├─ 苏州软件公司候选
│  ├─ 杭州信息技术公司候选
│  ├─ 物联网公司候选
│  └─ 其他专业单位
├─ 国际/其他司法辖区单位（仅展示已经关联的目录）
├─ 集团已确认 / 单位待归属
├─ 关联服务商与供应商（不当集团自有资产）
└─ 无关、冲突、待人工复核
```

苏州软件公司不自动归江苏省公司，杭州信息技术公司不自动归浙江省公司。香港单位不因为集团关系就取得项目 15 的授权；项目 3 中名为香港的候选行也要按本项目 scope 单独判断。省级目录不默认生成台湾/香港/澳门等辖区授权或未导入单位的任务。

两个可同时筛选的视角：
- **管理/法律归属视角**：谁拥有、管理或运营这个资产，应该派给哪家单位。
- **服务地域视角**：系统服务哪些省市，部署/机房在哪，涉及哪些区域的数据。

跨省统一业务可以“总部管理、服务全国、涉及浙江和江苏”，不能强迫单选一个省。仅有地域名称的线索，也允许“涉及浙江、单位未确认”。

## 3. 实体目录：用户确认一次，后续按目录聚合

每个单位保留 entity_id、group_id、parent_id、entity_kind、规范法律名称、统一标识（用户已有时导入）、辖区、省市代码、简称/英文名/历史名称、有效期间、业务品牌、官方域名/邮箱域、确认来源与版本、人工排除别名。

实体类型至少：group、headquarters、province_company、city_branch、county_branch、professional_subsidiary、overseas_entity、supplier、unknown。组织代码与地域代码分列；市公司也可能只是分支机构，不能一律虚构独立法人。

初始化提供 CSV/JSON 目录导入与人工编辑。允许用户导入已有省市公司清单；系统从 company 字段提出目录草稿，不能把文本聚类直接固化成法律层级。保留原 company，不用规范名覆盖它。括号全半角和空白可规范化匹配，行政词、法人后缀不能无差别删掉后再合并同名机构。

别名要绑定实体与有效期。例如“集团品牌”只用于候选检索，“浙江移动”仅在目录确认后指向对应单位；名称中有“移动”“杭州”不够。历史更名、合并/拆分和外包公司保留关系及时间，不重写原观察。

## 4. 资产到集团/省市的分配方法

分三步，分别保存结论：
1. 集团成员关系：group_confirmed / group_candidate / unrelated / conflict / unknown。
2. 管理归属：entity_confirmed / entity_candidate / shared / unknown；保留多个候选及证据。
3. 执行资格：沿用现有项目授权与暴露面 scope。第 1、2 步不自动赋权，不把域名发现直接变成可扫描资产。

证据优先级建议：

| 证据 | 用途 | 不能推出的结论 |
| --- | --- | --- |
| 用户确认目录/内部资产台账，绑定原 asset_id | 可建立高可信管理关系 | 台账归属不自动增加扫描权限 |
| 官方站点明确主体、官方域名目录、可信登记主体 | 支持集团/单位候选或人工确认 | 一个官网页面不足以证明所有同 IP 系统 |
| 官方子站/业务路径明确地市单位，并有集团主体证据 | 支持省/市候选 | 城市关键词或站点标题不能单独确认 |
| 公司名/品牌名/页面页脚 | 候选线索 | 不一定是自有系统，可能只是供应商展示 |
| IP 地理位置、ASN、网段、WHOIS 网络运营关系 | 辅助地域/基础设施视角 | 集团运营商客户资产不等于集团自有资产 |
| 相同证书、域名、图标、网页内容/CDN | 技术簇/查重线索 | 不传递组织归属、授权或敏感结论 |

第一次输出可确认、候选、冲突、待归属四个队列；候选默认不批量升级为 confirmed。人工确认保存理由、原证据、操作者、版本和生效范围，自动再算不得覆盖人工决定。

应当明确拒绝的分配：外企租集团云 IP→集团资产；某地址在杭州→浙江省公司；软件子公司服务全国→只属于注册地址省公司；同公共后缀→同组织；CT 新名字→已授权资产；集团 brand 命中→所有关联省自动可扫描。

## 5. 三种聚合分别算，不混成一个“簇”

1. **组织聚合**：集团/管理单位/省市，是任务和整改分发视图。
2. **技术聚合**：规范 endpoint、注册域、服务/证书等，帮助减少重复资产工作；不同端口/协议/业务系统不能盲目合并。
3. **泄漏事件聚合**：同一原文件、仓库 commit、观察内容的转载位置聚合为一件事件，保存各位置、时间和证据。

一个事件在 GitHub、文库和网页镜像被转发，集团风险总数只计一次事件，三个传播位置分列。涉及多个单位时分别标影响范围；省级数字是“涉及本省事件数”，不可直接相加当集团唯一事件数。共享资产同理按唯一 asset_id/规范实体身份去重，省分配量使用明确关联边计算。

当前 clusters.rs::registered_domain 仅取最后两个标签，必须改为带版本的 Public Suffix List 解析（含 com.cn/co.uk 及需要的 private suffix），不能把无关 *.com.cn 归为同一家；并保留旧聚类版本，不把新聚类结果当历史事实。PSL 也只给域名边界，不证明公司归属。[PSL 官方说明](https://publicsuffix.org/list/)

## 6. 排查方向：信息类别 × 渠道 × 单位

不要把“GitHub”“员工信息”“暗网”塞进一个分类字段。它们分别是渠道、信息对象和事件渠道。每个线索至少三个维度：信息类型、发现来源、归属/影响单位。

| 信息方向 | 具体目标 | 常见载体 | 不应直接算泄漏的例子 |
| --- | --- | --- | --- |
| 内部业务资料 | 内部制度、流程、未公开经营报表、合同正文、报价、内部系统手册 | 文库、网盘分享、官网误传、外包交付文档 | 官方宣传、公开服务说明、普通公司名 |
| 技术与网络资料 | 内部拓扑、设备清单、配置、资产清单、管理入口与内网地址组合 | 技术文档、仓库、博客附件、公开文件服务器 | 公开架构介绍、教材案例、单个公共 IP |
| 源代码与开发交付 | 非公开业务源码、配置、CI 文件、构建/调试日志、源码映射、代码包 | GitHub/Gitee/GitLab、Gist、镜像、发布包 | 集团正式开源项目、第三方 vendor 包 |
| 身份凭据 | 密钥、密码、连接字符串、会话/访问凭据、授权文件 | 配置、代码历史、日志、粘贴站、泄漏报告 | 明确占位/已替换的示例；只保存必要脱敏证据 |
| 员工与协作数据 | 未公开通讯录、工号、人员身份组合、内部 HR/协作资料 | 文档/分享、第三方泄漏、外包代码/交付 | 官网公开领导简介、公开岗位咨询联系方式 |
| 客户与业务数据 | 客户名单、业务记录、订单、用户身份与联系方式组合、导出的数据库/表格 | 公开分享、存储、备份、样本、泄漏情报 | 已匿名统计、公开客服入口 |
| 文件与存储误暴露 | 数据库/压缩包/备份、目录列表、开放对象存储、日志/报错附带内部数据 | 已授权自有站点、公开分享入口 | 网站本就公开的图片/手册 |
| 被盗/售卖/泄漏传播 | 售卖声明、勒索受害声明、带原数据依据的泄漏/stealer 情报 | 威胁情报 feed、公共声明、用户提供报告 | 只有集团名或卖家声称“有数据” |
| 仿冒与冒用（独立子模块） | 仿冒官网/品牌、钓鱼或冒用员工身份 | 公共网站、公开社交渠道、域名情报 | 一般报道/正常引用商标，不混入内部资料泄漏数 |

重点先做前七类；售卖/暗网接入需要可用情报源，仿冒可以独立排期。开放入口、安全配置或普通漏洞是“技术暴露”，与已发生的信息泄漏分别计数，不向每个 200 响应生成泄漏结论。

## 7. 来源覆盖：哪些要做，当前哪些还没有

| 来源方向 | 设计接入 | 检索/绑定依据 | 第一版行为与限制 |
| --- | --- | --- | --- |
| 自有公网资产 | 复用已有被动 Web/明确授权入口 | project asset、origin、scope 版本 | 只检查已获准读取的原入口，不绕认证或扩大到内网 |
| CT、历史网页 | 保留现有来源 | 已知域名和实体目录 | 用来发现名字/历史位置；过期页面不当当前可达证明 |
| 代码平台 | GitHub、Gitee、GitLab 等逐个适配 | 已确认企业 org/repo、企业域名、公开业务标识 | API/公开索引允许的内容；仓库、提交历史、Gist/Issue 各列覆盖，不声称一个接口覆盖全平台 |
| 文档/文库 | 各文库及公开文档索引逐个平台适配 | 单位别名+特征词+内部文档标识 | 能取正文才分类；只有题名保留 metadata_only，付费/不可取正文列未核验 |
| 网盘/协作分享 | 公开分享与用户提供分享清单 | 已观察分享链接、原文件 hash、主体信息 | 不猜提取码、不绕私有分享；只能看标题时不称全文泄漏 |
| 公开技术社区/粘贴/附件 | 允许索引/站点范围的公开内容 | 内部系统名、企业域、可信内容指纹 | 区分员工公开经验、外包交付与真正内部内容 |
| 企业账号泄漏情报 | 已验证域名的泄漏/stealer 数据接口、用户报告 | 企业邮箱域与获准目录 | 返回事件关系，不试密码、不把第三方账户泄漏说成集团服务器被入侵 |
| 暗网/盗取售卖情报 | 授权威胁情报 API/feed，安全导入原报告 | 已知域名、组织别名、业务特征、脱敏样本 | 单列来源覆盖和可信度；缺渠道/账号时 not_connected，不能报“未泄漏” |

网站名只是计划中的适配对象，当前 sources 仍只有三类。不能因为可以搜索某名字就把平台标 ready。每个新适配器登记 API/索引来源、权限、限额、条款/正文可取得程度、分页游标、覆盖时间和依赖状态。第三方站点是 source provider，不属于集团自有 target；其访问配置与集团目标授权分开，重定向仍逐跳检查。

GitHub 官方 secret scanning 区分自有仓库与 enterprise public monitoring 的覆盖，不能把自有 repo 告警当平台全域搜寻结果。[GitHub 官方说明](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)

HIBP 域名查询要求证明域名控制及 API 授权，其泄漏/stealer 事件接口不是全暗网索引，也不返回用户密码。设计上可作为企业账号泄漏的一路证据，不作为集团数据失窃证明。[HIBP 官方 API](https://haveibeenpwned.com/API/v3)

## 8. 关键词与查询包：每家单位独立，集团共用一次

集团查询包：确认的全称/简称/历史名、集团根域和企业邮箱域、业务品牌、内部系统名、用户提供的不敏感文档特征。省市查询包：目录内具体单位全称/别名、确认子域/业务入口、单位内部系统标识、文档单位字段。专业子公司另有查询包。

把省公司名与信息特征组合，是产生候选任务的方法，不是命中即泄漏。员工查询以企业域和受批准的企业账号为起点，不生成大规模私人手机号/私人邮箱搜索任务；内部真实秘密不发送给搜索引擎或模型。

共享平台查询按 query pack/source/window 去重。同一集团公共域，不给每个省重复跑一遍；获得候选后再按文档正文和资产关系分配单位。查询本身有版本与预算；新 unit/新别名修改不能重置已花费量，重跑以新任务记录绑定旧证据。

## 9. 招标与其他正常公开信息：明确排除

用户要求的硬边界：招标网、招投标/中标/采购公告、正常公开的招标附件不纳入此暴露面排查范围。

- 默认不为招标来源建立采集任务，不读取附件；无论是否出现集团、员工姓名、采购金额、业务系统名，都不计泄漏候选或风险数。
- 搜索/镜像偶然带回的公开招标信息，记 excluded_public_tender，仅保留最少排除依据与计数，不变相通过另一渠道纳入。
- 正常年报、官方公告、公开宣传、招聘 JD、已批准开源项目/公开论文，归 ordinary_public / approved_public，不计泄漏。
- 排除可依据原发布来源、文档类型、发布用途、内容 hash/转载关系和人工决定；单个关键词“采购/招标”不足以判断所有内容类别。
- 组织目录采用用户台账、官方组织名录等，不依赖被排除的招标网抓取。
- 如以后另行授权招标材料专项检查，单独启用项目策略与版本；当前不能以“可能敏感”为由自动绕过本次排除要求。

排除不会删除资产，也不会删除已有历史观察。正常公开被排除时仍显示原因，避免用户怀疑来源没跑或任务漏掉。

## 10. 泄漏证据与判断：四个问题分别回答

每条线索分别评估：①是不是集团资料？②涉及哪家单位？③内容是否应当公开？④是否真实向范围外披露？不能用一个总分把四个问题混在一起。

证据阶梯：

| 级别 | 实际取得证据 | 允许结论 |
| --- | --- | --- |
| metadata_only | 搜索题名、摘要、原位置，无可核正文 | 疑似线索，未核验内容 |
| content_observed | 可读取的脱敏正文/样本与来源、时间、hash | 已观察公开内容，组织/敏感性仍可待核 |
| leak_supported | 内容、主体、非正常公开用途都有可追溯依据 | 有依据的泄漏候选，需人工/独立复核 |
| leak_confirmed | 指定复核人按原证据确认、存版本/理由 | 已核实泄漏，可进入整改 |
| rejected_or_public | 正常公开、样例、无关、伪造等依据 | 不计泄漏，保留审计 |

“员工企业邮箱出现在第三方泄漏库”说明该账号关联某事件，不说明集团系统遭入侵；“真实公开的凭据样式”说明凭据泄漏候选，不说明该密钥仍有效；“只有域名/公司名/客户公开标识”不足以支持泄漏。不得通过登录企业系统验证被盗账号/密码。密钥当前有效性由有权限的资产责任方确认及轮换/撤销记录解决。

模型可解释相关性、敏感性与候选单位；必须引用原 observation，不能凭模型记忆创建资产/单位/泄漏确认、不能制造来源或核验状态。

## 11. 暗网与非正常渠道：展示真实证据程度

给用户独立的“泄漏情报”页签，分公开泄漏声明、地下售卖/暗网情报、盗取日志三类。优先接授权情报数据及原始报告导入，不自建交易/购买/联系卖家流程，不使用被盗凭据，不执行恶意样本。

至少记录：provider 与报告 id、原声明时间/首次发现/最近核验、频道类别、来源可信度、组织归属依据、所称数据类型和所称数量、实际取得的样本数量、样本是否能匹配公司或内部记录、疑似历史数据重复售卖、验证人及验证结论。

“卖家声称 100 万客户数据”与“核实样本 5 条”必须分字段展示。没有样本：unverified_claim；脱敏样本与单位匹配：sample_correlated；内部责任方确认事件：incident_confirmed。假称/伪造/旧事件复售分别记 rejected/fabricated/relisted。第三方已确认案例可保存其证明等级，但不能无条件转成我方确认。

报告影响省份根据样本/业务字段归属，不根据卖家所在地。集团名出现但省份未知→集团待归属。客户数据与员工数据分类分开；证据最少化、敏感内容遮盖，原件访问留审计。渠道无接入/欠费/接口失败/配额不足都显示具体未覆盖状态，不能用 0 件宣称暗网安全。

## 12. 逐省工作台：一轮怎么排查

省工作台显示本省管理单位及服务地域影响，用户可切换二者。

1. 核对单位目录和现有资产：确认、候选、冲突、待归属、关联供应商分别统计。
2. 展示可执行资产与未授权资产，不把关联资产数当实际扫描数。
3. 选择本轮来源和信息方向，冻结目录/归属/授权/查询包/配置版本与预算。
4. 在受批准的自有资产被动排查，同时查询已接入外部来源；集团公共查询共享复用、省查询独立记账。
5. 正常公开/招标排除→集团相关性→敏感性→证据→省市分配；待确认不阻塞其余明确单位。
6. 线索按风险排序：带凭据/客户数据/内部网络配置优先；只有题名的低证据线索不压过明确敏感正文。
7. 人工复核，分派给实际管理单位；共享系统派总部并标受影响各省，不把每省生成一份重复整改。
8. 整改绑定原事件与位置；复测新观察不改旧证据。删除某个转载位置不自动关闭其他位置或同一泄漏事件。
9. 出具本省报告：单位目录版本、资产归属清单、方向×来源覆盖矩阵、确认/待核/正常公开排除、未覆盖及原因、整改与复测。

滚动方式：第一轮基线；后续按新增资产、实体/授权变化、代码提交/新文档、来源新事件做增量。紧急确证凭据/客户数据事件立即派单，不等全国轮次收口。具体每日/每周频率按来源成本与用户工作需要配置，不创建自动定时任务。

## 13. 页面应当长什么样

集团页主导航建议：**组织与归属 / 省市排查 / 泄漏事件 / 内容与传播位置 / 情报渠道 / 排除记录 / 整改复测**。

左侧组织树：总部、省级公司/地市、专业子公司、待归属、供应商/无关。顶部保持 project selector，项目 3 与项目 15 不能因集团视图隐式合并。

集团总览卡片：候选资产、集团已确认、管理单位已分配、待归属/冲突、可排查、已核实泄漏事件、待核线索、未覆盖来源、未完成整改。旁边明确单位与去重口径，不只给一个风险分。

省表每行：省/单位、确认资产、待归属、可执行、实际检查、确认事件、待核、未覆盖方向、责任人与最新核验。缺组织目录的省不是 0 风险，而是目录未就绪。

覆盖矩阵示例（仅布局，不是当前测得数字）：

| 浙江省 | 自有站点 | 代码平台 | 文库/网盘 | 账号泄漏 | 暗网情报 |
| --- | --- | --- | --- | --- | --- |
| 内部资料 | 已查/有正文 | 部分覆盖 | 配额截断 | 不适用 | 未接入 |
| 源码/凭据 | 已查 | 已查/有候选 | 待查 | 已接入 | 未接入 |
| 员工/客户资料 | 部分覆盖 | 待查 | 有待核线索 | 已查 | 未接入 |

可点每格看 expected / planned / completed / failed / blocked / skipped、范围与时间、游标/配额、结果证据。不把只取得前 200/500 行标成该方向完成。只适配 GitHub 时“代码平台”卡明确 GitHub，Gitee/GitLab 各自 not_connected。

线索详情固定回答：什么内容、在哪里公开、为何可能属于集团、为何属于本省、为何不是正常公开、当前证据级别、受影响对象、什么时候发现/核验、哪些位置仍在、下一步责任人。原文默认脱敏，不展示真实密码、完整名单或失窃数据库。

## 14. 数据模型与核心合同（设计，不自动改共享表）

建议暴露面专属新表/合同：
- exposure_entities：组织目录与版本。明确与共享 asset ownership 目录如何关联；未确认前为候选层。
- exposure_entity_aliases / entity_identifiers：别名、已确认域名/邮箱/业务标识、来源与有效期。
- exposure_asset_entity_links：project_id、asset_id、entity_id、关系类型、候选/确认状态、证据、版本、人工锁定。
- exposure_asset_region_links：服务地域/部署地域与证据，不混成 entity_id。
- exposure_query_packs / source_capabilities：查询包与来源接入能力、限额、正文/时间覆盖。
- exposure_artifacts / source_occurrences：原 observation/hash、文档/仓库/报告位置、发布时间、首次发现和核验时间；不复制敏感全文到普通表。
- exposure_incidents / incident_entity_impacts：唯一事件、信息类型、确认级别、来源传播位置、多单位影响边。
- exposure_publication_exclusions：策略版本、原来源/文档类型/hash、原因（含招标硬排除）。
- exposure_campaigns / coverage_cells：project、unit/region、目录与 scope 等冻结版本、阶段结果与未覆盖。
- exposure_intelligence_reports：外部原报告 id、卖家声称数量/实际样本数分列、可信度和原依据。

已有 runs/work_items/observations/findings/cluster/remediation 延续使用，迁移尽量增加关联表，不重写资产原行或旧观察。新增模型预算、财务、Broker 或全局表由主控处理；Qoder先交 migration/IPC/TS 合同再集成，不能私自修改共享 schema。

候选事件合同至少：projectId、scopeVersion、directoryVersion、sourceKey、sourceReceipt、originalArtifactHash、observedAt、infoType、publicationState、groupRelation、candidateEntityIds、affectedRegionCodes、entityEvidenceRefs、leakEvidenceLevel、claimedCount、verifiedSampleCount、excludedReason、currentAccessibility、reviewRevision。敏感样本默认只引用受控证据位置。

## 15. 与现有授权和 Native Master 的连接

组织分配是呈现与任务规划，不改变 existing asset_ownership_decisions.authorization_status/exposure_eligible。集团 catalog 不能当跨项目授权清单。province assignment 不能扩 origin、port、method 或解除 private destination 拒绝。

新被发现集团域名/仓库/网盘文件先进入候选线索；自有目标要经过已有授权入口。第三方平台的只读查询使用单独 source-provider 配置；内部文件、员工名单、秘密不得完整发送外部模型。模型角色必须复用主控共享 Native/Broker/预算，未接入显示 not_ready。

请求/字节/文件数量、来源配额、模型费用分别记账。缓存命中可以少读已取得内容，不能证明仍获授权、仍可公开访问或仍未整改；必须保留 fresh observation 与历史缓存的区别。

## 17. 必须通过的关键例子

- asset.company='中国移动通信集团浙江有限公司'：先浙江候选；有主体/确认依据后归浙江省公司。标题仅“杭州”时城市未知。
- company='中移（杭州）信息技术有限公司'：专业子公司候选，服务浙江可为地域标签，不是省公司。
- 网段/ASN 登记为集团，页面为客户企业：关联基础设施/供应商或未知，不成为集团确认业务资产。
- 集团统一门户承载多个省入口：总部/共享一次资产管理，多省影响边，集团总数不重复。
- 浙江内部文档在外部代码仓库：资料归浙江，托管平台为来源，仓库所有者不被强制当资产所有者。
- 招标平台和转载站上同一中标文件：两位置均公开招标排除，不能因转载渠道换名重新计风险。
- 已批准开源仓库普通代码：正常公开；其中新增不应公开的凭据作为不同内容独立候选，不用整个 repo 白名单掩盖新秘密。
- 文库只可看到标题：metadata_only，不能算全文获取或已核实泄漏。
- 用户授权的企业邮箱在第三方泄漏情报中：企业账号关联事件；来源事实与集团系统遭入侵结论分开。
- 暗网帖子声称一百万条、实际只取得五条脱敏样本：声称与样本分别展示；未做内部核对则不确认一百万条。
- 某省查了自有入口但没有网盘/情报来源：覆盖矩阵 partial/not_connected，不能称该省泄漏排查完成。
- 香港与大陆项目：组织目录可以显示关系，执行和查询包预算保持各项目原 scope，跨项目请求拒绝。
- 同一文件多来源转载：一个泄漏事件、多位置；一位置被移除，其他仍公开则整改未关闭。
- PSL co.uk/com.cn/private suffix 与 IPv6/不同端口用例：技术聚合正确，仍不传递法律归属。
