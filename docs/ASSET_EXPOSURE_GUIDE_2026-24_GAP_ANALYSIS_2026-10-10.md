## 0. 判定口径与范围

**范围规则（用户原话）**：“我们当前的要求是外网暴露面，内网相关的或者登录主机那些直接忽略就行”；“pdf中涉及到的关于应用安全的，像什么弱口令，xx漏洞这些不包含在我们当前的暴露面功能中”。据此以下三类只在文末单列“不在范围”，不计入差距：

1. 内网、登录主机、终端、堡垒机、主机加固类；
2. 应用安全类：弱口令、各类漏洞、渗透、代码审计、WAF 配置；
3. 纯管理制度类：组织职责、考核、培训（产品能提供支撑的注明一句）。

**边界说明（本文的取舍，供评审）**：
- 附录一虽是“漏洞防护建议”，但其中几处本质上是**外部可观测的暴露面事实**，本文按在范围处理：敏感信息泄露中的“代码上传开源平台”“资料上传网盘对外分享”“建设暴露面资产发现能力发现互联网泄露”；软硬件公开漏洞中的“自有资产指纹清单”；违规开放互联网远程访问中的“高危端口 / 未明确用途端口 / 不安全管理协议 / 不安全密码算法”；网站黑链 / 网页篡改中的“不良信息页面 / 链接”。其余漏洞类条目一律不在范围。如评审认为这些也属应用安全，可整体移入第 9 节，汇总数字相应调整。
- 第三章“风险评估内容 / 评估周期 / 整改时限”针对漏洞评估，按不在范围处理；但“资产重要性分级”属于资产台账属性，按在范围处理。

### 1.1 最重要的 8 个缺口

1. **资产类型只覆盖 Web / IP / 域名**：小程序、公众号、移动 APP、邮件服务、独立 API 资产没有采集、台账和归属依据（对应条款 1、4、32）。
2. **没有资产重要性分级（0–4 级 / 定级备案级别）**：台账无级别字段，因此也做不到“0 级临时资产在线不超过一周”提醒，覆盖与整改无法按级别排序（条款 16、17）。
3. **没有“报备台账 ↔ 发现结果”比对与稽核**：不能识别未备案 / 未报备私自上线的资产，也不能把上级 / 第三方通报导入后与自有资产对账（条款 10、11、20）。
4. **端口与协议风险规则缺失**：FOFA 已采到 port / protocol / server / product，但没有高危端口清单、不安全管理协议（Telnet / FTP / SNMPv1）、TLS 弱算法、安全设备管理口、内部管理 / 运维 / VPN 入口的识别规则；也没有自有的主动端口探测（条款 14、18、26–29）。
5. **云资源归属识别缺失**：不能判断资产部署在移动云 / IT 云还是外部公有云，更无法识别“员工个人名义购买云资源部署公司资产”（条款 12）。
6. **泄露发现渠道窄**：网盘 / 文库关键词搜索不支持；文档只能读用户指定的公开 HTML / 文本 URL，PDF / Office 不解析；代码平台只有 GitHub，且代码搜索从未做真实验收；舆情来源未接入（条款 22–24）。
7. **台账缺用途、责任人、运营 / 运维单位，归属只有“一个归属单位”**：指南的“谁主管 / 谁运营 / 谁所有”三角色及判定顺序、合同约定归属有效期、ICP 备案主体作为“管理者”依据均未建模（条款 4、5、8、13、33）。
8. **没有常态化巡检调度与事件分级时限**：暴露面采集需人工点“开始”，无定时任务；事件 / 整改只有状态，无分级、无整改期限、无报送流程（条款 9、20、21）。

## 2. 第一章 总则

### 条款 1　一（三）1 暴露面资产的范围与类型
- **原文摘录**（p2–3）：“可从公共互联网被直接探测、访问或交互的各类数字资产……如 WEB 服务、邮件应用、小程序、公众号等；面向公网提供的 API 接口服务，如短信 API、直播接口、移动 APP 及后台等”；“包括但不限于 IPv4/IPv6 地址资产（含域名资产）、小程序、公众号与移动 APP 等资产类型”。
- **判定**：部分满足
- **依据**：
  - 台账字段只有 host / link / ip / port / protocol / domain / title 等（`src-tauri/src/db_schema.rs:693–717` `assets` 表），资产来源是 FOFA 测绘（`jobs/native_fofa.rs:378`）+ HTTP 探测（`jobs/native_probe.rs:419 probe_assets`），即 Web 与 IP:端口类资产。
  - 非 HTTP 端口有 `tcp_alive_non_http` 分桶（`jobs/native_workers.rs:306–319 optimize_src_assets`），邮件等服务只能以“端口 + 协议”形式出现，没有“邮件应用”类型。
  - 小程序 / 公众号 / APP：未找到证据。
  - IPv6：采集和探测代码未找到对 IPv6 的专门处理（只有暴露面出站门 `exposure/scope.rs:442` 拒绝 IPv6 ULA / 链路本地地址），未找到 IPv6 资产覆盖的测试。
- **差距**：缺小程序、公众号、移动 APP、邮件、API 四类资产的发现、台账字段与归属依据；IPv6 覆盖无证据。
- **建议**：资产表增加 `asset_type`（web / ip_port / mail / api / mini_program / official_account / mobile_app）；小程序 / 公众号先支持“导入 + 人工登记认证主体 + 后台域名”，APP 先支持“导入应用商店链接 / 包名 + 运营单位 + 后台域名提取”；后续再评估对接第三方小程序 / APP 测绘源。FOFA 查询补 IPv6 用例（`ip=` 带 v6 地址）并加测试。

### 条款 2　一（三）1 仅纳入境内资产
- **原文摘录**（p2）：“文中暴露面资产仅限部署在中国境内（不含港澳台）互联网上的资产，境外资产暂不纳入。”
- **判定**：部分满足
- **依据**：归属画像有“地域 / 排除地域”（`asset_ownership_profiles.jurisdictions_json / excluded_jurisdictions_json`，`db_schema.rs:732–746`），评估时读取 FOFA 返回的 country / region / province 做地域证据（`asset_ownership.rs:264、292`）；组织目录有 `overseas_entity` 实体类型和“境外”导航桶（`ownership_review.rs:442–451`，测试数据 `ownership_directory.rs:1653` 香港公司）。
- **差距**：地域只作为归属证据之一，不是“暴露面纳入范围”的硬过滤；无 IP 地理库，依赖 FOFA 字段；港澳台的单独口径未找到证据。
- **建议**：在暴露面计划阶段增加“境内 / 境外 / 港澳台 / 未知”地域标签（优先本地 IP 地理库 + FOFA 字段交叉），统计口径默认只计境内，境外与未知单列。

### 条款 3　一（四）资产归属单位必须明确、可追溯
- **原文摘录**（p3–4）：“暴露面资产的安全防护工作应由资产所属单位负责组织开展……由资产归属单位负责开展安全防护工作，并承担相应安全管理责任。”
- **判定**：满足
- **依据**：
  - 组织目录（集团 / 省 / 市 / 县 / 专业公司 / 境外 / 供应商）与项目绑定：`db_schema.rs:781–837`，`commands/ownership_directory.rs`。
  - 归属分析、聚合复核、组确认（只写归属不写授权）与逐条审计：`ownership_review.rs`、`ownership_operations.rs:882 apply_ownership_group_decision`；O2 §2–§4，O3「实现」。
  - 逐资产权威单位投影：`ownership_unit_projection.rs:79 ownership_asset_unit_projection`、`:87 ownership_asset_unit_edge`；O3 追加段；暴露面事件按投影关联单位，专业公司不并入省（`exposure/units.rs:106 place_unit`，测试 `tests_g4.rs:648`）。STATUS C-16、C-17、C-23。
- **备注**：“满足”仅指“每个资产能确认到一个目录单位并留痕”。指南要求的判定依据与角色见条款 4–7。

### 条款 4　一（四）1 “谁主管，谁负责”的判定依据
- **原文摘录**（p3）：“在工信部通信网络安全防护管理系统和/或工信部 ICP 备案系统中的资产备案单位，微信小程序、公众号的企业认证主体，移动 APP 的业务运营单位，视为资产管理者。子域名等备案资源借给外部单位使用的，备案单位同样视为该资产的管理者。”
- **判定**：部分满足
- **依据**：自动归属依据是“确认根域名 / 目录官方域名 / 共享域名 / 名称别名 / 证书组织 / ASN 组织 / 地域”（`asset_ownership.rs:227–330`，O2 分类器 `ownership_review.rs:324 ownership_classifier`）；子域名按 PSL 可注册域归组（O2 §4），因此“备案主域名下的子域名归备案单位”可通过确认根域名实现。
- **差距**：
  - 不使用 ICP 备案主体或通信网络安全防护管理系统定级备案单位作为依据：FOFA 只给备案号，未找到备案号→主体的查询（`asset_ownership.rs` 未引用 icp 字段）。
  - 小程序 / 公众号认证主体、APP 运营单位：无对应资产类型（见条款 1）。
- **建议**：增加“备案信息”只读来源（导入工信部备案导出表，或接入合规的备案查询接口），把“备案号 → 主办单位”作为强证据写入归属证据；证据类型标 `icp_filing_entity`，与证书组织、域名并列；“借给外部单位使用的子域名”默认仍归备案单位，归属复核时显示提示。

### 条款 5　一（四）2–3 “谁运营 / 谁所有”及判定顺序
- **原文摘录**（p3–4）：“资产运营/运维单位为中国移动内部单位的，视该运营/运维单位为资产运营者”；“资产运营/运维单位为外部单位，未在工信部系统中备案，但实际为中国移动内部单位业务并存在大量宣传物料的，视相关业务部门为资产所有者”；“原则上，资产依次以资产管理者、资产运营者、资产所有者的顺序判定资产归属”。
- **判定**：不满足
- **依据**：归属决定只有一个状态 / 单位（`asset_ownership_decisions`，`db_schema.rs:748–761`；投影只给一个 ownerEntityId）。未找到“管理者 / 运营者 / 所有者”三类角色字段，也未找到按顺序判定的规则。
- **差距**：无法记录同一资产的备案单位、运维单位、业务所有部门，也无法按指南顺序自动选出归属单位；“存在大量宣传物料”这类所有者证据没有对应证据类型。
- **建议**：归属证据增加 `role`（manager / operator / owner）与来源；归属单位由规则按 manager → operator → owner 顺序推导，推导结果与理由写入审计；人工可覆盖并留理由。宣传物料可复用暴露面已有的文档 / 网页观察作为 owner 证据引用。

### 条款 6　一（四）多单位协作资产协商另定归属
- **原文摘录**（p4）：“对于涉及集团内部多个单位/部门协作的资产，各相关方协商一致后，可另行确定其中一方为资产归属单位”。
- **判定**：部分满足
- **依据**：目录支持 `shared_domain` 标识（`db_schema.rs:807`），共享域名只给“attributed 52”且带反证（`asset_ownership.rs:297–300`）；O2 分组对 `multiple_entities` / `entity_mismatch` 进 conflict 车道（`ownership_review.rs:596、612、704`）；人工确认可带理由（O3「实现」5）；暴露面事件可同时关联多个单位（`exposure_incident_entities`，G4 §1 G4-0）。
- **差距**：没有“协商结果”对象（参与方、约定的归属单位、依据文件、生效时间），冲突车道里人工选定一方后，协商依据只能写在理由文本里。
- **建议**：在归属复核的 conflict 车道增加“协商确定”动作：选择参与单位与最终归属单位，上传 / 引用依据，记录生效与到期时间（同时满足条款 33）。

### 条款 7　一（四）仅提供软硬件资源、不参与运维的单位不纳入归属
- **原文摘录**（p4）：“仅提供软硬件部分资源，实际不参与系统运维的集团内部单位不纳入归属认定范围。”
- **判定**：部分满足
- **依据**：ASN / CIDR / IP 组织只算弱证据，理由写明“仅证明网络登记或运营关系，不等于业务资产”（`asset_ownership.rs:46 network_only_ownership_candidate`、`:305–307`；测试 `asset_ownership.rs:511 asn_cidr_and_ip_only_assets_are_weak_network_evidence`）；PSL 私有后缀托管平台记为 `private_suffix_tenant` 并带反证 `hosting_platform`（`ownership_review.rs:509`，O2 §4）。
- **差距**：这些规则防止“按 IP 段 / IDC 归属”，但没有显式的“资源提供方”关系类型，例如移动云 / IDC 提供机房但不运维的场景无法标注为“排除出归属候选”。
- **建议**：目录或归属证据增加 `resource_provider` 关系；命中时从候选归属单位中剔除并在复核页说明。

### 条款 8　一（五）2 持续性原则：资产清单要素与持续监测
- **原文摘录**（p4）：“各单位应建立暴露面资产清单，明确资产基本信息、用途、归属部门与责任人，并持续性开展对暴露面资产变化与安全情况的监测工作。”
- **判定**：部分满足
- **依据**：
  - 基本信息：`assets` 表（`db_schema.rs:693–717`），含 first_seen / last_seen / last_alive；归属部门：条款 3。
  - 变化监测：每次采集写 `new` / `changed` / `missing` 资产事件（`jobs.rs:512、521`；`jobs.rs:547 mark_missing`，摘要“本次完整采集未再次发现；不等同于资产已下线”）；重新探测流水线 `jobs.rs:629 execute_reprobe_job`；事件列表 IPC `commands/assets.rs:760 list_asset_events`。
- **差距**：清单没有“用途”“责任人（姓名 / 联系方式）”字段（全仓检索“责任人 / responsible / importance”在资产与归属模块中未找到）；变化监测需人工发起采集（未找到定时调度，见条款 20）。
- **建议**：资产或项目资产增加 `purpose`、`owner_contact`（责任人、部门、联系方式，按数据保护要求脱敏存储）、`operator_entity_id`；资产变化（新增 / 消失 / 标题或端口变化）生成待处理提醒，并可按归属单位推送到其清单视图。

### 条款 9　一（五）3 全面性原则：所有暴露面资产纳入防护体系
- **原文摘录**（p4–5）：“所有暴露面资产均应纳入安全防护体系，并定期开展风险评估与安全巡检。”
- **判定**：部分满足
- **依据**：暴露面覆盖矩阵如实给出 planned / executed / uncovered / failed 等分母，缺口不变绿（`exposure/coverage.rs:266 coverage_matrix`，钻取 `:562 coverage_drilldown`；STATUS C-41–C-43）；计划外资产显示为缺口（FIX4 P1／R3）。
- **差距**：覆盖只反映“暴露面泄露采集”的执行范围，不反映“资产是否已纳入防护（WAF / 白名单 / 评估）”；“定期”没有调度（见条款 20）。风险评估本身不在范围。
- **建议**：资产台账增加“纳管状态”（已报备 / 已纳入评估 / 已纳入巡检）由外部系统导入或人工维护，覆盖矩阵新增“未纳管资产”行。

## 3. 第二章 暴露面资产管理

### 条款 10　二（一）暴露面梳理：定义、归属认定、发现、梳理、报备、稽核
- **原文摘录**（p5–6）：“《中国移动互联网暴露面资产报备工作规范（2025 版）》……对各单位暴露面资产的定义、归属认定、发现、梳理、报备和稽核等工作流程给出了说明。”
- **判定**：部分满足
- **依据**：发现（FOFA 测绘 `native_fofa.rs:378`、探测 `native_probe.rs:419`、CT / Wayback 待归并）、归属认定（条款 3）、梳理（P1–P3 / Q1–Q3 分层 `native_refinement.rs:36`、O2 聚合复核）、导出（`asset_export.rs:78`、暴露面台账 `export.rs:313`）。
- **差距**：
  - **报备**：无与集团报备平台对应的字段与导出格式，未找到“报备状态”。
  - **稽核**：无“已报备清单 vs 实际发现”的差异报告（漏报、错报、已下线仍在报备）。
  - 未读取《报备工作规范（2025 版）》本身（不在输入中），字段口径需对照该规范补齐。
- **建议**：增加“报备台账”导入（CSV / Excel），与发现结果按 host / IP:端口 / 备案号对齐，输出三类差异：未报备在线、已报备未发现、字段不一致；导出格式按报备规范模板；差异项进入归属复核或整改队列。

### 条款 11　二（二）1 资产上线管控：识别未备案 / 未报备私自上线
- **原文摘录**（p6）：“资产备案/报备、系统安全评测、安全防护措施验收等……避免无防护上线。建议各单位在相应考核问责制度建设中，将系统未备案/报备资产私自上线纳入考核扣分内容。”
- **判定**：不满足
- **依据**：资产事件能标出“首次在项目中发现”（`jobs.rs:512`），但未找到与备案 / 报备清单的比对。安全评测、验收、考核属于制度 / 应用安全，不在范围。
- **差距**：产品无法给出“未报备即上线”的资产清单，考核扣分没有数据支撑。
- **建议**：依赖条款 10 的报备台账；对 `new` 事件且不在报备台账内的资产，自动标“疑似未报备上线”，按归属单位汇总，导出时附首次发现时间与证据。

### 条款 12　二（二）2 云资源使用：内部云优先、个人名义云视同私搭乱建
- **原文摘录**（p7）：“应使用移动云、IT 云或各单位自有云资源等集团内部资源……对员工个人名义购买非集团内部云资源，并用于部署公司资产的，后续将视同私搭乱建系统进行通报。”
- **判定**：不满足
- **依据**：FOFA 已采到 `org`（ASN 组织）与 `cname`（`native_fofa.rs:15、22`），归属评估把 ASN 组织当弱证据（`asset_ownership.rs:305–307`）；暴露面规则只能把页面里引用的对象存储地址标为存储线索（`exposure/rules.rs:248 storage_host`）。未找到“云厂商识别”或“非集团云部署”判定。
- **差距**：无法回答“哪些自有资产部署在外部公有云上”，更无法识别个人名义购买的云资源（外部无法直接观测购买主体，只能用证书主体、备案主体、页面主体与云厂商 IP 段交叉推断）。
- **建议**：维护云厂商 IP 段 / ASN / CNAME 后缀表（移动云、IT 云标为集团内部），给资产加 `hosting_provider` 与 `hosting_internal` 标签；对“已确认归属 + 外部公有云 + 无备案主体或备案主体为个人”的资产生成“疑似私搭乱建”线索，进人工复核。

### 条款 13　二（二）3 老旧废弃资产清理
- **原文摘录**（p7）：“对已废弃业务系统及时下线；对责任人已离职或调转的业务系统及时更新信息，无人负责的系统需下线处理；将仅内部员工使用的系统迁入内网；对使用频率极低……的系统建立清单并定期核查使用情况”。
- **判定**：部分满足
- **依据**：`last_seen` / `last_alive` 与 `missing` 事件（`db_schema.rs:714–716`、`jobs.rs:547`）；重新探测（`jobs.rs:629`）；分层里“Q2 强归属历史档案 / Q3 名称历史档案”区分过旧或无有效响应资产（`native_refinement.rs:104–121`）；资产软删除与回收站（`commands/assets.rs:645 soft_delete_assets`）。
- **差距**：无责任人字段，无法识别“责任人离职 / 无人负责”；无“仅内部员工使用系统”识别（如登录门户、OA、内部管理后台特征）；使用频率无法从外部观测，未提供导入入口；无“长期在线但无人认领”清单。
- **建议**：基于条款 8 的责任人字段做“无责任人 / 责任人失效”清单；增加页面特征规则识别内部办公 / 管理入口（标题与登录表单特征），列入“建议迁入内网”清单；支持导入业务侧访问量做低频清单；“连续 N 次未发现 / 未存活”生成下线确认任务。

### 条款 14　二（二）4 白名单防护：内部管理、运维接口不应暴露互联网
- **原文摘录**（p8）：“除必要面向公众开放的宣传页面与业务服务外，其余站点与服务接口建议根据业务的实际适用范围设置白名单防护……单位内部管理、运维使用的服务接口原则上不应暴露在互联网，可采用 VPN 拨入后使用。”
- **判定**：不满足
- **依据**：探测只给存活 / 状态码 / 标题 / 不良内容分类（`native_probe.rs:222 probe_one`、`native_content.rs`）；检索 login / admin / 后台 / vpn / 管理系统 在采集与探测代码中未找到识别规则。白名单是否生效需从多地源探测，未找到相关能力。VPN 账号源地址白名单属账号 / 内网接入，不在范围。
- **差距**：无法列出“暴露在公网的管理后台、运维接口、数据库 / 中间件管理端口、VPN 门户”，也无法验证“省内业务仅限同省 IP”。
- **建议**：增加“管理 / 运维入口”识别规则（标题、路径、登录表单、典型产品指纹，如 Jenkins、Kibana、Nacos、各类 VPN / 防火墙登录页），结果作为暴露面线索按归属单位汇总；可选：从不同出口地域发起只读探测，比对可达性差异，判断白名单是否生效（需授权与出站门约束）。

### 条款 15　二（二）5 同类功能资产合并
- **原文摘录**（p8）：“对于同类型功能的业务系统……建议开展系统功能合并改造……或将系统映射在单一公网 IP 地址的不同端口/目录并统一开展安全防护。”
- **判定**：部分满足
- **依据**：暴露面按证书 / 域名 / 内容聚类（`exposure/clusters.rs:185 content_clusters`、`:217 domain_clusters`，PSL 边界 `:66 registrable_boundary`）；采集分层也做簇（`native_refinement.rs:159 write_clusters`）；簇面板 IPC `page_exposure_clusters`（`exposure.rs:1414`）。
- **差距**：聚类用于归属与去重，没有“同类功能系统”视角（同标题 / 同指纹 / 同一产品多实例）的合并建议，也没有按单位统计“可合并资产数”。
- **建议**：基于 title + product 指纹 + favicon hash 生成“同类系统”簇，作为收敛建议报表输出（不自动合并资产）。

## 4. 第三章 暴露面风险评估（仅资产分级部分在范围）

### 条款 16　三（一）资产重要性分级（0–4 级）
- **原文摘录**（p9–10）：“可将其重要性划分为 5 个不同的等级，其中 4 级最高，0 级最低……已在工信部通信网络安全防护系统中进行过定级备案……其重要性应直接沿用定级备案级别……建议各单位在梳理自有暴露面资产时，同步标注资产的重要性级别”。
- **判定**：不满足
- **依据**：`assets` / `project_assets` / `asset_ownership_decisions` 均无重要性或定级字段（`db_schema.rs:693–761`）。`review_tier`（P1–P3 / Q1–Q3）表示**归属置信与活跃度**，不是重要性（`native_refinement.rs:36–121`）；暴露面线索的 `severity` 是线索严重度（`exposure/schema.sql:116`），不是资产级别。
- **差距**：无资产级别，无法“沿用定级备案级别”，也无法按级别排序覆盖、事件与整改。
- **建议**：项目资产增加 `importance_level`（0–4）、`level_source`（定级备案 / 单位预估）、`filing_ref`；支持导入定级备案清单自动带级别；覆盖矩阵、事件队列、导出增加按级别筛选与统计。

### 条款 17　三（一）0 级临时资产在线不超过一周
- **原文摘录**（p10）：“预估为 0 级的临时资产在线时间原则上不应超过一周。”
- **判定**：不满足
- **依据**：有 `first_seen` / `last_alive`（`db_schema.rs:714–716`），但无级别字段（条款 16），未找到相关提醒。
- **差距**：无法发现“超过一周仍在线的临时资产”。
- **建议**：在条款 16 基础上，对 0 级资产按 `first_seen` 与最近一次存活计算在线天数，超过 7 天生成提醒 / 线索。

## 5. 第四章 暴露面防护措施（仅外部可观测部分在范围）

### 条款 18　四（一）1 双栈策略疏漏与安全设备运维端口暴露
- **原文摘录**（p13）：“一是在 IPv4 与 IPv6 双栈共存期间防火墙策略可能产生的配置疏漏；二是防火墙自身的安全防护，不建议使用默认口令或将运维端口暴露在互联网。”
- **判定**：不满足
- **依据**：未找到同一资产 IPv4 / IPv6 暴露面对比；未找到安全设备（防火墙 / VPN / WAF）管理口识别。默认口令属弱口令，不在范围。
- **差距**：无法从外部发现“IPv6 侧多开的端口”或“安全设备管理界面暴露在公网”。
- **建议**：对有 AAAA 记录的域名分别采集 v4 / v6 端口与标题，输出差异；在条款 14 的管理入口规则中加入主流安全设备指纹（深信服、网御、网神、天融信等管理页特征），命中即作为高优先级暴露面线索。

## 6. 第五章 暴露面监控与检测（仅外网暴露面部分在范围）

### 条款 19　五（二）威胁情报数据运用（与暴露面相关的泄露 / 售卖情报）
- **原文摘录**（p18–19）：“多源情报的接入、整合与运用……一是威胁情报的自动化分析处置，包括情报信息标准化、去重关联、严重性评级……二是情报数据生命周期管理。可考虑为情报构建自有的置信度标签、业务领域标签、过期失效标签等，并制定过期失效机制”。
- **判定**：部分满足
- **依据**：公开情报导入（JSON / CSV，`imports.rs:212 parse_intel`），系统定级 claim_only / sample_supported，`human_verified` 必须人工带锚点（`imports.rs:276 intel_grade`、`:890 grade_intel_finding`；IPC `grade_exposure_intel` 已注册，G4「P0 落地」）；同内容多位置去重为一个事件（`incidents.rs:471`）。
- **差距**：只有手工导入，未接入任何情报 feed；只覆盖“泄露 / 售卖声明”，不含 IP / 域名 / URL / IOC 情报（这部分偏 SOC，可视为范围外）；无过期失效标签与机制；无与自有资产（IP / 域名）的自动关联命中。
- **建议**：情报记录增加 `expires_at` 与业务领域标签，过期后自动降级；增加“情报中的域名 / IP 与自有资产台账匹配”规则，命中生成事件并关联归属单位；选一个合规的公开情报源做真实 adapter。

### 条款 20　五（三）常态化安全巡检（自建、周期短、资产识别准确）
- **原文摘录**（p19–20）：“外部单位对本单位资产识别不准确，导致通报范围实际上存在大量疏漏……对某特定单位而言巡检周期过长，难以保证第一时间发现安全隐患。因此自建常态化安全巡检能力仍是各单位有效提升安全防护能力的优先之选。”
- **判定**：部分满足
- **依据**：可按项目反复发起暴露面采集 / 复测（`exposure.rs:1176 start_exposure_scan`、`:1196 resume_exposure_scan`，`remediation.rs:318 start_retest`）与资产重新探测（`jobs.rs:629`）；覆盖矩阵支持最近一轮 / 7 / 30 / 90 天窗口（REM §1）；归属门禁让“本单位资产”识别有依据（条款 3）。
- **差距**：
  - 无定时 / 周期调度（检索 cron / schedule / 定时在暴露面与采集模块中只出现在规模测试 `tests_g4_scale.rs`）。
  - 无外部通报（两部委远程检测、第三方通报、集团巡检）的导入与“通报 ↔ 自有资产 ↔ 归属单位”对账。
  - 巡检纳入附录一漏洞、人工参与等属应用安全，不在范围。
- **建议**：增加项目级巡检计划（周期、来源、额度、时间窗），由后台按计划创建轮次，沿用现有冻结计划与授权检查；增加“外部通报导入”，按 URL / IP / 域名匹配资产与归属单位，未匹配的进入“疑似漏识别资产”队列。

### 条款 23　附录一（三）敏感信息泄露 · 常见问题（7）内部资料上传网盘并对外分享
- **原文摘录**（p32）：“相关人员将内部资料、数据上传到各类网盘中，并设置对外分享。”

- **依据**：网盘关键词搜索、登录、提取码在能力表中固定为 unsupported（G3 §3；`exposure/coverage.rs:100` 能力行 `netdisk_keyword_search`，测试 `tests_g3.rs:1001`）；被动网页能把页面里出现的 `pan.` / `drive.` 链接标为存储线索（`rules.rs:248–266`）；已知分享链接只能作为“指定文档 URL”读取（仅 HTML / 文本）或手工导入。
- **差距**：不能主动发现网盘对外分享；即使拿到分享链接，网盘页面多为动态渲染 / 需提取码，现有读取能力基本拿不到正文。

### 条款 24　附录一（三）敏感信息泄露 · 防护建议（11）建设暴露面资产发现能力，发现处置互联网泄露
- **原文摘录**（p33）：“应建设暴露面资产发现能力，结合舆情监测、态势感知等多种手段，及时发现并处置泄露在互联网上的本单位工作文档、业务数据、系统代码等敏感信息，并完善相应问责机制流程。”
- **判定**：部分满足
- **依据**：资产发现（FOFA，条款 10）；泄露发现：被动网页规则（凭据、业务 Source Map、可疑文档、存储 / 仓库链接，`rules.rs:317 findings_for`）、CT / Wayback、GitHub、指定文档 URL、文件 / 情报导入；分类与正常公开排除（招采、领导介绍、开源等，`classify.rs:389 classify`，STATUS C-11–C-14）；事件去重、单位关联、处置闭环（条款 21）；覆盖矩阵如实显示未实施渠道（STATUS C-41）。
- **差距**：舆情 / 搜索引擎 / 文库来源未接入；PDF / Office / OCR 不解析（STATUS U-31）；问责只能靠“通知登记 + 单位关联”，没有责任人与时限；被动采集观察 URL 里凭据参数仍原文落库（STATUS U-04，高）。
- **建议**：优先补 PDF / DOCX 文本解析（有界、无宏执行）；接入一个搜索引擎 / 舆情来源做“文档标题 + 机构名”发现；事件关联资产责任人（依赖条款 8）；先修 STATUS U-04。

### 条款 25　附录一（三）软硬件公开漏洞 · 防护建议（1）自有资产指纹清单
- **原文摘录**（p34–35）：“梳理构建自有资产指纹清单，明确自有资产所使用的系统、组件、产品类型、型号、版本；对自研产品需明确其是否存在外部代码引用并加以记录”。
- **判定**：部分满足
- **依据**：FOFA 专业版字段 product / product_category / product.version / server / icon_hash / jarm / banner_hash / header_hash（`native_fofa.rs:19–27、59–80`，`fofa_fields` `:335`），导入时写入 `assets.extra_json`（`jobs.rs:379–382`）。
- **差距**：指纹完全依赖 FOFA 返回（且需专业版档位）；无本地指纹识别；`extra_json` 没有结构化的“组件—版本”清单视图、检索与导出列（资产导出只含 company / host / ip / port / protocol / domain / title 等，`asset_export.rs:85–100`）；“自研产品的外部代码引用”属软件成分分析，不在范围。
- **建议**：把 product / version / server 提升为可检索字段或独立指纹表（资产 × 组件 × 版本 × 来源 × 时间）；提供“按组件查资产”视图与导出，便于漏洞预警时快速定位受影响资产（漏洞匹配本身不在范围）；评估接入本地指纹库对探测响应做二次识别。

### 条款 26　附录一（三）违规开放互联网远程访问 · 常见问题（1）重要设备高危端口对互联网开放
- **原文摘录**（p39）：“重要设备在公网暴露有高危端口……包括 80/135/136/137/138/139/443/445/593/1434/4444/5554/8080 等。”
- **判定**：部分满足
- **依据**：FOFA 返回每条资产的 port / protocol（`native_fofa.rs:4–6`），台账有 `assets.port`（`db_schema.rs:700`），可在资产列表中按端口查看。
- **差距**：无高危端口规则与告警；无“重要设备”标记（依赖条款 16 与《两清两固》重要设备清单）；端口数据完全依赖 FOFA 的被动收录，时效与完整性不可控，未找到自有主动端口探测。
- **建议**：增加可配置的高危端口清单（默认按指南列表），对“重要设备 / 级别 ≥ 某值”的资产命中即生成暴露面线索；提供在授权范围内的轻量主动端口核验（只对已确认归属且已授权的 IP，限端口集合与速率），用于确认 FOFA 结果是否仍有效。

### 条款 27　附录一（三）违规开放互联网远程访问 · 常见问题（2）未明确用途的服务或端口
- **原文摘录**（p39）：“重要设备在公网暴露有未明确用途的服务或端口”。
- **判定**：不满足
- **依据**：资产无“用途 / 登记端口”字段（条款 8），无法判断“未明确用途”。
- **差距**：缺少“登记用途的端口清单”与“实际观测端口”之间的比对。
- **建议**：随条款 8 / 10 增加“报备端口与用途”，与实测端口比对，差异项即“未明确用途端口”线索。

### 条款 28　附录一（三）违规开放互联网远程访问 · 常见问题（3）不安全、业务未使用的管理协议端口
- **原文摘录**（p39）：“重要设备在公网暴露有启用了不安全的、业务未使用的管理协议端口，如 SNMPv1、Telnet、FTP 等”。
- **判定**：部分满足
- **依据**：FOFA protocol 字段可显示 telnet / ftp / snmp 等协议（`native_fofa.rs:6`），落入台账 `assets.protocol`；非 HTTP 存活桶 `tcp_alive_non_http`（`native_workers.rs:314`）。
- **差距**：无协议风险规则；SNMP 为 UDP，FOFA 收录有限，产品无 UDP 探测；无法区分“业务使用 / 未使用”。
- **建议**：增加“不安全管理协议”规则（telnet、ftp、snmp v1/v2c、rlogin、明文 VNC 等），命中生成线索；SNMP 版本识别需主动探测，纳入条款 26 的授权内轻量核验。

### 条款 29　附录一（三）违规开放互联网远程访问 · 常见问题（4）管理端口使用不安全密码算法
- **原文摘录**（p39）：“重要设备在公网暴露有使用不安全密码算法的管理端口。不安全密码算法包括 MD5、SHA-1、DES、3DES、RSA-1024 及以下、ECC-224bit 及以下、IKEv1”。
- **判定**：不满足
- **依据**：FOFA 证书字段只有 subject / domain / sn / is_valid / is_match / is_equal（`native_fofa.rs:9–13、64–66`），未采集签名算法、密钥长度、TLS 套件；探测未做 TLS 握手分析（`native_probe.rs`）。
- **差距**：无法发现弱签名算法证书、短密钥、弱套件或 IKEv1。
- **建议**：在授权范围内对 HTTPS / 管理端口做 TLS 握手只读检查（证书签名算法、公钥长度、协商协议与套件），按指南列表判定；IKEv1 识别需 UDP 500 探测，单列为后续能力。

### 条款 30　附录一（六）网站黑链 / 网页篡改（不良信息页面与链接）
- **原文摘录**（p46）：“(2)站点被植入/某页面被替换为反动页面/不良信息页面；(3)站点某页面被植入反动页面/不良信息页面链接”。
- **判定**：部分满足
- **依据**：探测阶段对页面内容做赌博 / 色情加权打分，带反例词（`jobs/native_content.rs:7–96`，`:128 score`），支持自定义关键词（`commands/assets.rs:460 add_content_rule`，`jobs.rs:87 dynamic_content_keywords`），结果写 `assets.content_category`，探测分桶 `blocked_content`（`native_workers.rs:315`）。
- **差距**：只检查探测到的入口页，不遍历站内页面，也不检查页面中的外链（黑链）；无“反动”类规则；无“与上次内容对比”的篡改检测；命中不进入暴露面事件 / 整改闭环。
- **建议**：对已确认资产的首页与 sitemap 页做定期内容快照与差异比对；对页面外链按不良域名库 / 内容规则检查；命中生成暴露面事件，复用现有复核、整改、复测闭环。入侵痕迹 / 木马检测不在范围。

### 条款 31　附录二 情况 1：内外部合作资产的安全责任归属
- **原文摘录**（p47）：“对移动内部单位与外部单位合作涉及的资产，除外部单位为事业单位，且出具盖章说明认领系统安全责任外，安全责任一律划归移动内部单位，无论该资产是否由移动内部单位进行运维。”
- **判定**：部分满足
- **依据**：目录有 `supplier` 实体类型（`db_schema.rs:790`），人工确认归属可带理由并审计（O2 / O3）；外部单位资产可通过排除规则排除（`asset_ownership.rs:293–296`）。
- **差距**：没有“外部单位类型（事业单位 / 企业）”与“盖章认领说明”证据项；没有“合作资产默认归内部单位”的规则，人工排除时也不会提示需要认领证明。
- **建议**：归属排除动作在“排除原因 = 外部单位”时要求选择外部单位类型；非事业单位或无认领证明时不允许排除，默认归内部合作方；认领证明作为附件引用写入审计。

### 条款 32　附录二 情况 2：小程序 / 公众号认证主体与后台域名分属两家单位
- **原文摘录**（p47）：“部分微信小程序、公众号存在企业认证主体为公司内部 A 单位，但使用的后台站点域名为公司内部 B 单位的情况……建议存在此种合作类型资产的单位与合作方尽早协商明确安全责任”。
- **判定**：不满足
- **依据**：无小程序 / 公众号资产类型（条款 1）。暴露面事件支持关联多个单位（`exposure_incident_entities`），但没有“小程序 ↔ 后台域名”的关系。
- **差距**：无法同时呈现 A（认证主体）与 B（后台域名）两条通报口径，也无法提示双方协商。
- **建议**：随条款 1 新增小程序 / 公众号资产，记录认证主体与后台域名列表；后台域名与已有域名资产关联，当两者归属单位不同时自动进入归属复核 conflict 车道并提示“需协商（附录二情况 2）”。

### 条款 33　附录二 情况 3：合同约定归属仅在合同有效期内有效
- **原文摘录**（p47）：“双方通过合同条款明确安全责任归属的情况。合同条款内容可视为双方‘取得一致意见’，但需注意若双方未签署补充协议，该‘一致意见’仅生效至合同有效期止。”
- **判定**：不满足
- **依据**：归属决定与组操作无有效期字段（`db_schema.rs:748–761`；`asset_ownership.rs`、`ownership_operations.rs`、`ownership_authorization.rs` 检索 valid_until / expires / 有效期均未找到）。
- **差距**：合同到期后归属不会自动失效或提醒。
- **建议**：随条款 6 的“协商确定”记录 `agreement_ref`、`effective_from`、`expires_at`；到期前提醒、到期后该资产回到归属复核队列并在统计中标“约定已过期”。
